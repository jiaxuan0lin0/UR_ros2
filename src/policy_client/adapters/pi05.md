# PI0.5 adapter (design notes)

**Status: not implemented.** There is no `policy_client.scripts.pi05` module, so `policy_script:=pi05` fails at startup with `No module named 'policy_client.scripts.pi05'`. This page records what a PI0.5-style adapter must provide and a proposed server contract. Confirm the real endpoint names, authentication, payload fields and image encoding against the actual PI0.5 server before implementing.

The robot-side loop is described in the [policy_client README](../README.md), the adapter interface in [README.md](README.md), and workspace setup in the [top-level README](../../../README.md).

## Robot-side requirements

| Item | Requirement |
| --- | --- |
| Action | 7-D `[q1..q6, gripper]`: absolute joint targets (rad) and a gripper **target** (not the next observed gripper state) |
| Gripper scale | Normalized 0–1 (default `gripper_input_mode=normalized`), 1.0 = open |
| Chunk timing | One row per `joint_point_duration_sec` (1/30 s by default); the robot interpolates to 500 Hz `servoJ` |
| Response | `action` (7) required; `action_chunk` (N x 7) and `history` optional |
| State | 7-D `observation.proprio`; convert in the adapter if the model expects another layout |
| Images | RGB `uint8` `(H, W, 3)` arrays; the adapter chooses the wire encoding |
| Reset | `reset()` must clear server-side episode state (`/policy_control/reset_policy`, and every `start`/`step` by default) |

## Proposed server contract

These endpoints are a proposal, not an existing API:

```bash
curl http://<POLICY_HOST>:<POLICY_PORT>/health
curl -X POST http://<POLICY_HOST>:<POLICY_PORT>/reset
```

`POST /act` request:

```json
{
  "instruction": "task text",
  "images": {"primary": "<encoded image>", "wrist": "<encoded image>"},
  "state": [0, 0, 0, 0, 0, 0, 0],
  "executed_actions": [[0, 0, 0, 0, 0, 0, 0]],
  "rtc_prefix_actions": [[0, 0, 0, 0, 0, 0, 0]]
}
```

`POST /act` response:

```json
{
  "action": [0, 0, 0, 0, 0, 0, 0],
  "action_chunk": [[0, 0, 0, 0, 0, 0, 0]],
  "history": {}
}
```

## RTC

`policy_client` already applies a robot-side RTC blend (`rtc_control_enabled`, `rtc_execution_horizon`, `rtc_transition_schedule`, `rtc_exp_decay`; see the [policy_client README](../README.md#control-loop)). It smooths the boundary between chunks at execution time. Model-side prefix guidance or inpainting, which makes the new chunk consistent with the previous one, has to be implemented in the PI0.5 server.

Two constraints for `rtc_prefix_actions`:

- The node does not pass the previous chunk to `act()`. An adapter that sends `rtc_prefix_actions` has to keep its own copy of the last `PolicyResult` (for example the tail of its `action_chunk`), or the node has to be extended.
- `executed_actions` holds **measured** `[q, gripper]` states sampled during execution, not the commanded actions.

## Implementation checklist

| Check | Requirement |
| --- | --- |
| Module | `src/policy_client/policy_client/scripts/pi05.py` defining `create_policy_client(*, base_url, timeout_sec, gripper_pad_value, **kwargs)` |
| Client class | Subclass of `PolicyClient` implementing `health`, `reset`, `act`, `record_action` |
| Image encoding | Identical to what the server decodes |
| Output | Converted to the robot's 7-D convention before `PolicyResult.from_response` |
| Timing | Chunk rows spaced at `joint_point_duration_sec` |
| Doc | Replace the proposal above with the real contract |

Once the module exists, launch it like any adapter (dry run first):

```bash
ros2 launch policy_client policy_joint_abs_control.launch.py \
  python_executable:=<PYTHON_EXECUTABLE> \
  robot_ip:=<ROBOT_IP> \
  policy_base_url:=http://<POLICY_HOST>:<POLICY_PORT> \
  policy_script:=pi05 \
  instruction:="<TASK_INSTRUCTION>" \
  rtc_control_enabled:=true \
  rtc_execution_horizon:=10 \
  rtc_transition_schedule:=exp \
  dry_run:=true
```
